# ETW 会话恢复

ETW 内核会话可能在 GameHelper 仍运行时被外部停止。事件处理线程退出会触发自动恢复；每 30 秒的健康检查同时检查会话是否存在、读取线程是否仍存活，并核对已观察到的游戏进程。

## 恢复与计时

- 每次会话故障最多尝试重建 3 次，分别等待 1、2、3 秒。每次失败立即释放部分初始化的资源。
- 恢复前后核对已观察到的进程。进程仍存活且创建时间不晚于其原始启动事件时继续跟踪；已退出或 PID 已被新的进程复用时补发停止通知，释放计时引用，后续同一游戏可以正常开始、结束新会话。
- 系统拒绝查询进程身份时保留记录，不把“无法查询”当成“已经退出”；之后的健康检查会再次核对。
- 补发停止无法还原准确退出时间，按核对时刻结算，因此可能包含中断至核对之间的额外时长；日志会记录 `Reconciling missing process stop` 警告。正常 ETW 停止事件仍按既有计时方式处理。
- 未收到启动事件的进程不自动补造会话；完全发生于观察空窗内的启动/退出无法还原。本机制也不会修改历史上已经丢失的会话。
- 连续恢复失败会输出 `process monitoring is DOWN` 错误。用户可以停止后重新启动监控；GameHelper 不会自动重启用户实例。

## 生命周期与隔离

恢复属于当前一次启动请求。恢复退避期间再次调用 Start 不会另建竞争会话；Stop/Dispose 会取消恢复。随后重新 Start 会创建新的运行世代，旧恢复任务、旧读取线程和已经排队的旧定时器回调均不能影响新会话。

进程回调与状态核对串行执行，保留原始启动事件的 PID、路径和时间。重复启动、过期停止以及旧读取线程的通知不会重复增加计时引用或终止新的 PID 身份。停止事件关闭时仍淘汰已退出进程，避免再次开启后使用失效记录。

会话名采用 `GameHelper-ETW-{ownerPid}-{guid}`。资源耗尽时只清理确认属主已退出的新格式会话。旧格式、格式不明、属主存活或无法确认属主状态的会话均保留，避免影响用户运行中的旧版本。旧版本自身仍可能执行不安全的前缀清理，新版本无法改变旧进程的代码。

## 验证

`EtwProcessMonitorRecoveryTests` 通过内部 ETW/进程查询接口和可控时间源执行真实监控状态机，无需管理员权限，覆盖取消恢复、并发启动、旧任务/回调隔离、最后失败清理、健康检查兜底、PID 复用及后续计时结算。

`EtwSessionLossIntegrationTests` 在管理员 Windows 环境创建独立监控实例、独立 CSV 目录和测试进程。只停止它明确创建的 ETW 会话，控制游戏在恢复空窗内退出，断言本局和下一局两条 CSV 记录，并确认其他 GameHelper 会话未被清理。ETW 测试集合只负责串行化；每个测试释放自己的监控实例，不进行全局会话清理。
