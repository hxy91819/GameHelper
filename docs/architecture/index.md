# GameHelper Architecture

GameHelper is a Windows-focused .NET 8 application for game launching, process monitoring, playtime tracking, and configuration-driven automation. The WPF library is the graphical shell; ConsoleHost owns the single automation runtime and CLI. The old WinUI design is retired and imposes no compatibility requirements on this design.

## System Shape

```text
 GameHelper.Desktop -- local named pipe --> GameHelper.ConsoleHost
        |                                        |
        +----------> Core / Infrastructure <-----+
```

- Shells own presentation, command routing, and desktop-specific user experience.
- `GameHelper.Desktop` owns WPF views, view models, local artwork, and separately persisted UI drafts. It constructs no monitoring or HDR/CE controller. The selected prototype is archived at `codex/wpf-library-prototype`.
- Steam artwork stays outside the automation runtime. Infrastructure resolves explicit Steam identity, reads public metadata and bounds/cache-writes downloads; Desktop decodes/freezes images and stores manual artwork associations separately from game configuration. Ambiguous names require a user choice. Read-only snapshots use caches; live network rendering tests are opt-in.
- Steam genre metadata also stays in the desktop presentation flow: Infrastructure bounds, throttles and caches best-effort store `genres`; Desktop joins only confirmed AppIDs, stores manual multi-genre overrides separately, and defaults to unclassified. Neither metadata fetching nor manual grouping enters the automation runtime.
- Local discovery is owned by `ILocalGameDiscovery`: Infrastructure bounds filesystem traversal, classifies executable evidence separately from installation state, and groups launchers/main binaries by game directory. Candidate strength comes from engine layout and title identity, never file size alone; ties stay unconfirmed, auxiliary programs remain available but hidden by default. Desktop starts with no selected candidates and allows one executable per directory, exposing reasons and requiring an explicit import. Installation evidence remains installed/missing/unknown. Core owns confirmed batch intake and revalidates paths before one catalog mutation; scans and display groups never alter configuration or history. Desktop defaults to installed games, retaining drafts across group changes. Explicit name-based artwork matching binds only one exact normalized title; batch work cannot replace an existing association.
- The read-only playtime dashboard aggregates one history snapshot in Core, using an injected clock and the existing local end-date convention. IPC returns bounded daily/monthly/calendar aggregates, up to 1000 ranked games and a focused game/date rhythm summary with Monday-first weekday totals. The desktop suppresses the optional legacy 30-row session payload and presents aggregates only. Desktop owns native charts, sorting/search and latest-request-wins cancellation; it never reads or mutates the CSV directly. See [dashboard semantics](../guides/playtime-dashboard.md).
- `GameHelper.Core` owns models, contracts, orchestration, catalog matching policy, settings, statistics, and monitor lifecycle coordination.
- `GameHelper.Infrastructure` owns concrete adapters for process monitors, YAML/CSV persistence, HDR control, DDC/CI monitor preset control, Steam resolution, and Windows startup integration.
- Per-game `actions` are ordered executable operations through `IGameLauncher.ExecuteAction`. Library launches run `beforeLaunch` on the caller thread outside the state lock, retaining the companion lock through preparation, actions and game launch; failure follows the HDR rollback path. There is no total Launch deadline: wait-enabled runs each allow 30 seconds, closes wait up to 4.5 seconds per matched process, and native/HDR/DS4 operations add their own time. External-start companion application can still wait for this lock on the event thread.
- **After-exit execution**: last-process session completion only enqueues immutable actions under the state lock. `AfterExitActionQueue` consumes them serially on a background worker without the companion lock; per-action admission validates the posted generation and registers an execution lease under the same state lock as Stop's invalidation. Stop closes publication before cleanup, then drains its captured worker outside all service locks for at most five seconds through `TimeProvider`; timeout or self-drain logs a warning and continues. An admitted native call may finish after Stop, but cannot admit another old action or publish state into a later lifecycle. A restarted worker awaits its predecessor, retaining one consumer even after a drain timeout. Channels are managed resources: completion and discarding queued references each use independent best-effort cleanup. Recovery of already-dead sessions never posts actions. Lock order stays update → companion/before-launch → state; queued admission adds no lock. The five-second limit covers after-exit drain, not companion-lock acquisition, before-launch I/O or other Stop cleanup.
- Controller-companion process operations stay inside `WindowsGameLauncher`: validate before HDR changes, start/reuse the configured executable when enabled, or close running DS4Windows instances when disabled before launching the game. External observations and in-flight recovery apply the same setting through `IGameLauncher`, logging failures without interrupting tracking. The adapter owns graceful exit, bounded termination, independent cleanup and sandbox process scope. Desktop stores the per-game path inside launch options and preserves it in drafts.
- Dependency direction is enforced by tests and documented in [Dependency Direction Rules](./dependency-direction.md).

## Primary Runtime Flows

- **Configuration**: shells call core catalog/settings services; infrastructure persists the compact `config.yml` shape (`monitor`, `startup`, `cheatEngine`, `breakReminder`, `monitorMode`, `hdr`, `sync`, `games`).
- **Monitoring**: `MonitorControlService` starts the process monitor and `GameAutomationService` as a lifecycle pair. Runtime process filters are derived from enabled game candidates and refreshed on config reload. ETW and WMI both keep expensive event enrichment behind this candidate-name gate. ETW sessions embed their owner PID and recover after external loss. Recovery retains observed process identities, reconciles missed exits and PID reuse, and emits stop notifications to release playtime references. Cleanup preserves live, legacy, and unknown-owner sessions.
- **Automation**: process events first pass a cheap executable-name candidate gate; full path resolution is lazy and only used for configured candidates that need path matching or disambiguation. WMI process detail lookup follows the same rule and is not performed for non-candidate start events. Metadata/fuzzy matching is limited to that candidate set. HDR changes require a library launch before process creation. External starts (including startup enumeration) still receive speed attachment, configured companion startup and monitor game presets, but never gain HDR ownership or late HDR takeover. In-flight recovery preserves launch provenance; legacy snapshots keep their continuity rule. Active game sessions drive playtime tracking, HDR scheduling, optional first-process speed application, and monitor preset-mode switching: during the configured daylight window an active game requests the game preset, everything else requests the comfort preset, both applied read-then-write over DDC/CI (stateless assertion with a self-healing tick). HDR scheduling only rolls back HDR changes made by GameHelper itself. Speed control uses the `IGameSpeedController` seam; the Windows adapter generates a PID-specific transient Cheat Engine table and launches the configured user installation.
- **Statistics**: playtime records are read from local files and joined to current config by stable `DataKey`.
- **Stats sync**: `SyncService` aggregates playtime into a report + daily CSV and pushes it through an upload channel (GitHub via local git.exe or REST API). A console background loop checks interval/mtime gates every 15 minutes; session-end paths perform no extra disk writes.
- **File drop**: duplicate app launches forward dropped files to the running console process, which updates config and reloads automation.

## Key Modules And Seams

- **Game Library module**: `IGameLibrary` is shared by the in-process application implementation and named-pipe client. ConsoleHost exposes it while monitoring for the WPF library. The pipe is user/config-scoped, uses current-user access controls, length-bounded JSON frames and deadlines. Requests cannot change the host's selected config. Saves use catalog revision checks inside atomic configuration changes; client mutation timeouts are not automatically retried. Desktop polling retains drafts and selection, and updates runtime state without rebuilding unchanged items.
- **Game Launch module**: `IGameLaunchCoordinator` prepares and confirms HDR before `IGameLauncher.Start`, and holds a two-minute pending launch until matching process observation transfers ownership to gameplay. The process match identity remains separate from `launch` target/arguments/directory. Failed or expired launches restore only owned HDR; an initially enabled HDR state is left enabled. Pending deadlines and HDR ownership persist with in-flight sessions, without replaying launch commands after restart. Disabled automation permits plain launches without HDR/speed/time tracking. DDC writes still stop whenever HDR is enabled or unknown. See [the decision](../adr/0002-wpf-library-and-launch-ownership.md).

Foreground break reminders have a separate in-memory clock from persisted process-session playtime. `GameProcessMatcher` provides read-only classification shared with automation. `BreakReminderService` uses `TimeProvider`, a foreground activity provider, and a notification seam; automation start/stop/reload drives its lifecycle. Sampling is serialized, matching caches include process creation identity and expire on configuration reload, and unavailable observations cannot establish a completed break. The Windows adapter checks the input desktop and compares uptime with unbiased interrupt time to exclude suspend intervals. Native system notifications own a background message loop and transient tray icons, released on reset and shutdown. ConsoleHost registers these services when it composes automation. See [Break Reminder](../guides/break-reminder.md).

ETW recovery owns a serialized lifecycle and process identity reconciliation, with an internal OS session/query boundary for deterministic testing. Adopted in-flight processes enter the same observation table before ETW starts. Durable snapshots include every process and its creation identity, refresh every ten seconds, and preserve completed rows when history writes fail. Monitor preset updates serialize separately from session bookkeeping, confirm writes by hardware readback, retry failures, and immediately re-evaluate configuration reloads. Sandboxed hosts never register system auto-start, and one-shot CLI commands leave it unchanged. See [ETW recovery behaviour](../guides/etw-recovery.md) for timing, cancellation, isolation, and known observation gaps.

- **Background and WPF startup entry**: the auto-start Run entry launches WPF `--background`, which starts `ConsoleHost monitor --background` without a console; an explicit desktop launch activates the WPF library, and a no-argument ConsoleHost launch opens it as well. The passive-launcher direction is retired; see [ADR-0002](../adr/0002-wpf-library-and-launch-ownership.md), [ADR-0003](../adr/0003-remove-console-interactive-ui.md), and [startup behaviour](../guides/startup.md).
- **Process Observation seam**: `IProcessMonitor` lets ETW, WMI, and no-op adapters satisfy one interface. ETW subscribes before capturing already running candidates, so games started before monitoring still enter automation; adopted PIDs are not emitted again, and queued starts older than the capture are ignored. `ProcessObservationPolicy` atomically configures candidate names and stop-event observation, so core automation never probes optional adapter capabilities. `IProcessPathResolver` keeps expensive live path lookup out of monitor callbacks; the ETW adapter also uses it at the gate to recover identity when non-ASCII image names garble in the ANSI kernel payload.
- **Game Configuration seam**: `IGameConfiguration` owns the complete `AppConfig` document through `Read` and atomic `Change`. YAML is the only runtime adapter; the former JSON adapter and `convert-config` were removed. Catalog and settings changes cannot overwrite unrelated document fields. `AppConfigValidator` in Core is the shared validation entry for whole-document transactions, settings updates and `validate-config`; it delegates existing section rules to their Core models. `SettingsService` lives in Core and references no Infrastructure code. `YamlConfigCodec` binds writable model properties directly, retaining only wire-name aliases, the `startup` envelope and ISO 8601 timestamp encoding in Infrastructure. There are no stored-field DTOs or template-based validation schema. YAML shape/type diagnostics remain in the adapter; value rules stay in Core. Loaded entries retain the existing skip/repair/ignore-invalid-optional-value policy, while failed changes never write the file. Normalization and catalog edits use `GameConfig.Copy()` and replace only changed values, automatically retaining future fields without changing the class's reference equality semantics. An optional `IConfigWatcher` seam (Windows adapter: `ConfigFileWatcher`) debounces file-system events on the config path and triggers `GameAutomationService.ReloadConfig`, so manual external edits hot-reload just like file-drop intake; the watcher skips absent-file windows and limits a failed reload to one retry, and monitor type plus sync-loop settings stay startup-bound.
- **Executable Identity and Game Catalog Intake**: `ExecutableIdentity` is one immutable stored value with read-only name/path projections. `IGameCatalogService` exposes list, preview, intake, batch intake, update, and remove outcomes; duplicate detection, `DataKey` allocation, and commit-time validation stay inside the module.
- **Playtime seam**: `IPlayTimeService` records sessions; `IPlaytimeSnapshotProvider` reads historical snapshots for statistics and session summaries. Both current adapters share one internal CSV codec for schema, escaping, and parsing; when the CSV is absent, the service performs a one-time import from legacy `playtime.json`.
- **File-drop Intake module**: Console file drops are validated, resolved, batch-committed through Game Catalog Intake, and followed by one automation reload. It uses explicit dependencies and does not construct storage or catalog implementations itself.
- **Automation module**: `GameAutomationService` coordinates matching, session tracking, playtime, HDR, optional speed control, monitor preset modes, and stop-event control.
- **Launch ownership collaborator**: internal `LaunchOwnershipCoordinator` owns the two-minute pending launch window, observed library-launch provenance, launch failures and `HdrScheduler` lease. `GameAutomationService` retains lifecycle/generation validation and delegates launch at the same two state-lock boundaries. All collaborator state borrows `_stateLock`; no additional lock is introduced. The nested lock order remains `MonitorModeCoordinator.UpdateLock → _companionLock → _stateLock`. HDR/launcher calls keep their existing state-lock scope; dependencies must not synchronously re-enter lifecycle methods.
- **In-flight recovery collaborator**: internal `InFlightSessionRecovery` owns session start times, persisted process creation identities, snapshot writes and throttled failure logs, startup adoption/closure, failed-history retries and recovered speed application. The suspend handler borrows its start dictionary under the same `_stateLock`, preserving one source for resume offsets and snapshots. The service keeps process/timer generation gates and stop ordering. Recovery adds no lock or I/O call site; snapshot schema/path and PID identity fallback remain unchanged (creation-time comparison is required only when the probe supplies it).
- **Automation event lifecycle**: each Start subscribes fresh process and power delegates carrying a generation; Stop invalidates them before best-effort unsubscription. A failed remover may retain an inert delegate, but it cannot register or end sessions in a later lifecycle. Maintenance callbacks also carry their originating generation. Companion operations check the same generation under a dedicated execution lock outside the state lock; Stop crosses that boundary before cleanup. Lock order is monitor update → companion → state for Stop, and companion → state for companion validation.
- **Automation speed lifecycle**: speed requests capture the current generation before immediate execution or deferred scheduling. Both controller entry and correlation-record publication check that generation. Stop invalidates it before draining; a callback surviving a drain timeout cannot borrow a later Start generation. Drain waits at most five seconds; timeout (including a drain requested inside its own callback) logs a warning and returns without throwing TimeoutException. Stop still flushes sessions, clears state and disables automation, so MonitorControlService completes its normal stopped-state transition. An external controller call already entered cannot be interrupted, but its late result is discarded. The five-second bound applies to drain only, not acquisition of lifecycle locks or immediate controller calls.
- **Game Speed Attachment module**: callers only request `ApplySpeed(pid, multiplier)` through `IGameSpeedController`; its result means an attach was initiated, not that the game's clock was verified. The CE adapter owns per-request table identity, atomic file publication, expiry cleanup, and process launch. Each request gets a unique table so queued or concurrent requests for one PID cannot overwrite each other. The private embedded Lua implementation owns Unity hook reuse and CE exit monitoring; tests exercise the same generated table through the controller interface, including opt-in execution in real CE.
- **Background startup**: deployment and published startup tests load `scripts/start-checked-instance.ps1`. WPF `--background` connects or starts the single runtime with `CreateNoWindow`, confirms IPC and exits. The helper checks the reported executable path before taking ownership, verifies no visible console, and supports restoring releases predating this entry. Existing WPF windows restore without activation.
- **Monitor preset mode seam**: `IMonitorModeController` lets no-op and real DDC/CI adapters satisfy one contract. `MonitorModePlan` is an immutable validated settings snapshot (ordered DDC/CI recipes plus a `DaylightEvaluator` over solar sunrise/sunset or fixed windows); the stateless `MonitorModeScheduler` reads the current VCP state and applies the recipe only on mismatch. DDC/CI bus I/O stays outside the automation state lock so a slow monitor cannot stall session bookkeeping. Daylight coordinates come from the manual config (highest priority), the Windows location service via `IUserLocationSource` when `location: auto` (detected once per start and cached through `ILocationCacheStore`, refreshed at most daily, falling back to fixed windows on failure), or the fixed time window. Defaults are calibrated for the Dell U2720QM and overridable per monitor. See [Monitor preset auto-switching](../guides/monitor-mode.md).
- **In-flight session continuity seam**: `IInFlightSessionStore` (atomic temp+rename JSON snapshot at `%AppData%\GameHelper\inflight-sessions.json`) persists live game sessions on every tracking-state change, so force-killed or crashed instances still recover them. On startup `GameAutomationService` delegates to `InFlightSessionRecovery`, which re-adopts sessions whose process identity still matches (`IProcessIdentityProbe` verifies the recovered pid's image path against the persisted identity, guarding against PID reuse) and resumes them from the original start time through `IPlayTimeService.ResumeTracking`; sessions whose game died during downtime are closed at the last-known-alive timestamp via `WriteRecoveredSession`, with the recovered span capped at 12 hours. Manual stop keeps the immediate-flush semantics and clears the snapshot. This is the safety net that makes the direct-update deploy policy safe.
- **Stats sync module**: `ISyncService`/`SyncService` own interval debouncing, mtime-based dirty checks, content hashing, and state persistence; `IStatsUploadChannel` implementations (git.exe runner and GitHub Git Data API client, both in Infrastructure) only write inside the configured remote subdirectory.
- **Shell modules**: CLI commands should call core services rather than duplicate domain logic; command routing stays separate from service construction.

Monitor preset automation calls `IHdrController.TryGetEnabled` before any DDC availability probe or preset read/write. The Windows adapter refreshes DisplayConfig state under its HDR lock, including manual changes; enabled or unknown HDR suspends the entire preset update. Suspension invalidates the change gate so the first confirmed SDR update re-evaluates even unchanged game/daylight state. DisplayConfig failures are unknown, not a confirmed SDR result.

## Persistence Model

- `config.yml` is the primary configuration file under `%AppData%\GameHelper\`.
- `dataKey` is the single stable game identity in configuration and the statistics key written to playtime records.
- Each game stores one `executable` value. It can be a full path for path-first matching or a process file name for name-only matching; `ExecutableIdentity` derives read-only path and name views from that value. An optional positive `speed` value requests Cheat Engine speed control on first process activation; the `speedAttach` policy (default `auto`) defers that attach behind the mod loader's chainloader completion marker when a loader is detected beside the executable, falling back to a timed attach and guarding against PID reuse during the wait. Game exits shortly after an attach are correlated with WER crash reports in the automation log.
- `playtime.csv` is the current playtime history format. Legacy `playtime.json` is imported once when the CSV does not exist; there is no JSON write path.
- `sync-state.json` records stats-sync bookkeeping (last success/attempt, content hash, target identity); it is written only after an upload attempt. The git upload method keeps its throwaway clone under `%AppData%\GameHelper\sync\`.
- Configuration changes reload the latest complete document, preserve unrelated fields, and commit through a temporary-file replacement. A failed change is not persisted.

### Adding a configuration field

For a game field such as nullable `int? LaunchDelaySeconds`, add the property in
`Core/Models/GameConfig.cs` and its nonnegative-value rule in
`Core/Validation/AppConfigValidator.cs`. YAML automatically uses `launchDelaySeconds`,
and normalization, catalog edits, file validation and transactions retain/check it.
No provider DTO, mapping, normalizer field list or YAML validation template needs editing.
A new exceptional wire alias belongs in the codec only when a wire name differs from
camelCase; new UI/CLI editing controls and feature behavior remain separate work.
Tests and user-facing field documentation accompany the feature as usual.

Tray presentation is split between Core `TrayMenuService` snapshots/action routing and the native Windows message window. Library reads and commands run on workers. Manual primary HDR uses `TrayHdrControl` and a controller-scoped weak lease registry shared with `HdrScheduler`; lock order is automation state → HDR lease gate → controller. Manual operations never re-enter automation. Scheduler prepare/update publishes ownership even on failure; startup recovery updates HDR before exposing the tray. Manual writes bypass automation target selection and never add rollback targets.
