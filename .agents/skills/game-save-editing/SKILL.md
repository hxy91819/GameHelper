# 本地游戏存档恢复与修改

这是代理操作流程，不代表 GameHelper 已内置存档编辑器。通用部分是定位、备份、转换与验证；字段结构和加密参数按游戏及版本适配。用户只要求恢复时，恢复操作不包含修改数值。

## 选择资料

- Peeping Dorm Manager v1.0.9 / Build 14020192：读 [已验证格式与案例](references/peeping-dorm-manager.md)，再用当前文件验证版本及格式。
- 其他游戏：读 [新游戏分析与适配](references/new-game.md)，记录证据后才建立对应游戏资料。

## 操作顺序

1. 明确游戏路径、目标字段与目标值。恢复任务则确认丢失表现。查运行进程、游戏元数据和日志定位候选存档，完成标准是有证据说明游戏实际读取哪个目录。
2. 核对路径视图。打包应用启动的进程可能读取 MSIX 私有缓存；常规路径与缓存的相同哈希不一定证明物理文件相同。对照独立文件系统视图和游戏日志，记录路径、大小、修改时间及 SHA-256。
3. 备份所有将替换的文件和配套系统文件到独立、不会覆盖旧备份的位置。游戏正常退出后重新读取并备份最终存档；退出可能触发保存。只有最终文件与分析基线一致时才写入。
4. 在副本上解析。核对字段原值；与用户报告不一致时重新检查存档槽、时间和路径，说明差异，不能宣称已确认原值。能解析 JSON 不等于找对字段；结合读写代码、配套结构或受控游戏行为确定语义。
5. 只更改授权字段。保留未知字段、序列化类型、嵌套编码和非目标记录；校验数值范围与实际存储类型。将目标变化与原始数据作结构化对比，要求变化集合恰好等于授权集合。
6. 重编码后反向解析，检查目标值与其他字段一致；格式允许时，先证明未修改的解码再编码可以得到原字节。写入前再次核对游戏已退出、源文件哈希未变，用同目录临时文件和替换操作写入，保留可回退备份。
7. 从实际目标路径重新读取、解密核验。把“文件校验完成”和“游戏读档显示正确”分别报告；没有游戏内证据时明确后者待确认。启动验证优先沿用用户正常启动方式，防止再次产生不同存档目录。

## 恢复与停止条件

恢复优先采用已存在的完整副本、自动备份或云存档，按进度证据选择；时间戳只作为线索。系统快照、回收站是后续候选。在线同步存在时先确认来源，避免旧云档覆盖恢复结果。

加密验证、结构校验或写入前哈希检查失败即停止写入，保留原件并说明缺少的证据。恢复失败时，报告已检查的候选及下一步；不要以重开游戏或新建存档代替恢复。

## 沉淀

将新游戏的引擎/版本指纹、实际路径、容器格式、算法参数来源、目标字段和验证范围写入 references，并从本文件链接。复用同类编解码器，保留逐游戏适配；不要把某款游戏的密码推广到所有 Unity 游戏。仓库只保留方法和脱敏样例，不收录玩家存档、日志、内存快照或下载的分析工具。
